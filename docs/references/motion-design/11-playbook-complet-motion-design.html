[advanced model] Motion Design: The Complete Playbook

Since [advanced model] dropped on September 22, my feed has been nothing but motion design: showreels, launch films, music videos, 3D loops. All of it rendered from code. Almost all of it captioned "one prompt".

Some of those really were one prompt. Most weren't. The gap between the two is what this article is about.

Here's the part most people miss. [advanced model] doesn't make videos. It can't output an MP4. It writes a program that draws every frame, a browser plays that program one frame at a time, and ffmpeg stitches the frames into a file.

So the quality of your video comes down to two things:

  1. The decisions you hand it. Every line you leave out, [advanced model] fills with a default. Those defaults are the "AI look" you've already learned to scroll past.
  2. The loop you let it run. When [advanced model] can render its own frames and look at them, it fixes what's wrong. When it can't, you get its first draft.

Thariq from the Claude Code team summed up that gap in one post:

I went through the posts that defined this trend and put everything into one playbook, so you don't have to reverse-engineer it from fifty threads. What each line of your prompt makes [advanced model] decide, what it falls back on when you're vague, how to make it check its own work, plus every prompt, number and script you need. All of it is copy-paste ready, and every script in here was actually run.

Part 1. What actually happens when you ask [advanced model] for a video

[advanced model] takes text and images in, and puts text out. That's the whole interface. So every clip in this trend is a program [advanced model] wrote, plus something that turned that program into frames.

Here's the pipeline, step by step:

  1. You write a brief: text, plus references if you have them.
  2. [advanced model] writes code. Usually it's one HTML file with a function seek(t) that paints the exact frame for time t.
  3. A headless browser opens the file and calls seek(0), seek(1/60), seek(2/60) and so on, once per frame.
  4. It screenshots every frame to a PNG.
  5. ffmpeg stitches the PNGs into an MP4 and adds the audio.

At 60 fps, a 15-second piece is 900 calls to seek(t). Nothing depends on a clock, so frame 512 looks identical on every run.

There are four routes from your brief to that MP4:

Route

What [advanced model] writes

Best for

Watch out for

A · Code-drawn

Canvas 2D, SVG, WebGL or p5 in one HTML file, rendered by headless Chrome

Loops under 15 s, kinetic type, abstract motion, 3D with Three.js

One file gets messy past ~1 minute. You own the render script

B · Framework

Remotion (React components) or HyperFrames (HTML + GSAP), rendered by their CLI

Series, templates, data-driven videos, anything over 30 s

Needs an install. Name it explicitly, or [advanced model] picks route A

C · Mixed pipeline

Calls to image or video models through their APIs, then compositing and redrawing on top in code

Characters, physics, realistic motion that's hard to hand-code

Needs API keys and a budget. Consistency lives in the code layer

D · Footage edit

Cuts, captions, B-roll and picture-in-picture over your own clips

Talking heads, product demos with real recordings

[advanced model] sees frames but can't hear speech. Give it a transcript with timestamps

Left alone, [advanced model] usually picks route A: one file, zero dependencies. If you want route B, say so in the first line, for example "a Remotion composition, 1080x1920, 30 fps, 600 frames".

Writing code instead of pixels sounds like a limitation. It's the opposite:

  • Every frame is reproducible. Render frame 84 twice and you get the same image twice.
  • Edits are cheap. You change one number and re-render one second. No re-rolling a video model and hoping.
  • [advanced model] can check its own work. It reads images well, and a contact sheet of your animation is just an image. That loop is what separates the viral pieces from the "mid" ones (Part 7).
  • The source is yours. The second video in the same project is always faster, because the renderer, the sound synth and the export pipeline already exist.

L1 · The one-liner

This was the most copied prompt of launch week:

plaintext
make a dynamic 15-second motion graphics video that shows what an incredible motion designer you are, like it's your showreel for a résumé. go all out.

Why it works so well:

  • "showreel for a résumé" sets a genre whose rules [advanced model] already knows: fast cuts, a new technique every shot, the best work first.
  • "what an incredible motion designer you are" makes the model itself the subject. There's no product to get wrong and no facts to check. Nothing can miss the brief, because there is no brief.
  • "15-second" means 6 to 8 shots, small enough to finish and polish in one pass.
  • "go all out" tells it to spend effort: more techniques, more polish passes. It pairs well with a high effort setting.

Why it falls apart the moment you point it at your brand: a one-liner tests the engine, never the idea. Thousands of people ran the same sentence, so the reels started to rhyme with each other: same tricks, same order. And when you swap in your product, the one thing that matters is the one thing the prompt never describes.

Rexan Wong hit exactly this wall. His one-prompt video looked mid, so he took apart how the good ones were really made:

If you still want a one-liner, give it a spine. Same size class, far fewer defaults:

plaintext
Make a 15-second motion graphics showreel, 1080x1080, 60 fps, one HTML file.
Warm off-white #F4F1EA, near-black #141413, one accent #D97757.
A new technique every 2 seconds, cuts on a 120 BPM grid.
Banned: gradients, glow, particles, text in the corners, everything fading in.
Show me one still per shot before the full render. Go all out.

L2 · The brand reel

Three extra lines turn a showreel into your launch video: your URL, your real assets, and music. Tony Dinh said he'd paid over $1,000 for a similar launch video a year earlier, and made his TypingMind reel with [advanced model] in under 30 minutes.

The line that matters most is about assets. If you don't give [advanced model] screenshots, it invents a plausible UI. Plausible is not yours.

plaintext
GOAL: a 20-second launch film for [PRODUCT] ([URL]) that makes [AUDIENCE] want to try it.

ASSETS: open the site with Playwright, screenshot the real UI, grab the real logo,
colors and fonts. Save everything to ./assets and list it before you animate.
Never redraw the product UI from memory. Crop and animate the real screenshots.

STORY (one beat each, 2-4 s):
1. Hook: the problem in 5 words or fewer, huge kinetic type.
2. The product appears and assembles itself piece by piece.
3. Three features, each one a real cursor action in the UI.
4. One number that proves it works: [METRIC].
5. Logo lockup + [CTA].

LOOK: brand colors only, one accent, [FONT]. Banned: gradients, glow, particles,
everything fading in, text in the corners.

SOUND: original 120 BPM track synthesized in code. Clicks and whooshes on the beats.

FORMAT: 1080x1920 first, then 1080x1080 and 1920x1080 from the same timeline.

QA: show me a contact sheet (one frame per beat) before the full render.

L3 · The state spec

The most bookmarked prompt of the week wasn't a one-liner. It was a spec. This UI morph is one shape that never cuts: it becomes a button, a loader, a player, a chart, and a cursor drives every change.

Why specs work so well: a state list removes interpretation. Every beat has a known start state, a known end state and a known duration. [advanced model] is executing your film, not guessing at it.

Here's my version of the structure. Fill in the brackets:

htmlbars
<goal>
A 16-second product loop for [PRODUCT] that makes [AUDIENCE] understand [ONE IDEA].
</goal>

<inputs>
Before writing code, ask me for: the 8-12 UI states that tell the story, the real data
shown in each one, brand colors (hex) and fonts, one accent, and a track near 120 BPM if I have one.
</inputs>

<direction>
One container that never cuts. Each state is the same element changing size, radius and fill
while its content swaps behind a 4-frame blur. A cursor causes every change with a real click,
drag or keystroke. Warm neutral canvas. Springs at damping ratio 0.8 for UI, 1.0 for text.
</direction>

<states>
120 BPM at 30 fps = 15 frames per beat. 8 bars = 32 beats = 480 frames.
Bar 1: logo -> pill button            Bar 2: button -> email field (typed)
Bar 3: field -> loader                Bar 4: loader -> success check
Bar 5: check -> dashboard card        Bar 6: card -> chart draws itself
Bar 7: chart -> command palette       Bar 8: palette -> toast -> logo (frame 479 flows into frame 0)
</states>

<build>
1. One HTML file, one <canvas>, window.seek(t). No CSS transitions, no timers,
   no state carried between frames.
2. Closed-form springs only. A value with several targets = the sum of one spring per change.
3. Text inside a morphing container enters 4 frames after the morph starts
   and leaves 4 frames before the next one.
4. State changes land on beats. Bigger changes land on downbeats (every 4th beat).
</build>

<bans>
Gradients on UI, glow, particles, bouncy easing on text, anything static for more than one beat.
</bans>

<qa>
Show me the state list on the beat grid before any code. Then render one still per bar
as a contact sheet, score it, fix the 3 worst problems, and only then do the full render.
</qa>

L4 · The director's brief

The most viewed [advanced model] music video came from Donald. He talked to his computer for five minutes, then Claude worked for 12 hours.

"One prompt" was technically true. But that prompt was roughly 9,500 characters of direction: a reference video, a song, tools and API keys, a workflow with gates, and a review loop. That isn't a prompt. It's hiring a crew. The full template is in Part 12.

How to climb the ladder:

  • Use L1 to test your setup, nothing more.
  • Move to L2 the moment your product is in the video.
  • Use L3 for anything you post as a brand.
  • Use L4 when the piece runs past a minute or has a story and characters.

Part 3. Inside [advanced model]'s head: what each line of your prompt changes

This is the most important idea in the whole article. Every line you write takes one decision away from the model. Every line you skip, [advanced model] makes itself, and its decisions drift toward the same few defaults.

Prompt line

What [advanced model] decides from it

If you leave it out, it defaults to

GOAL

What the viewer should feel or do, and what to cut

"Impressive", so it adds more effects instead of a clearer story

OUTPUT (engine + canvas)

Code architecture, file layout, resolution

One HTML file at whatever size its first idea suggests. Changing the canvas later means re-directing every shot

TIME (seconds × fps)

Shot count, pacing, frame math

Loose pacing, and durations in milliseconds that don't land on frames

BEAT GRID (BPM)

Where cuts and hits go

Cuts wherever a shot feels done. No rhythm

PALETTE (hex)

Every fill, stroke and light

A dark background, a purple-to-blue gradient and one bright accent

TYPE

Hierarchy, and how text enters and leaves

A big bold sans-serif, centered

MOTION (easing, springs)

How everything accelerates and settles

Ease-in-out on everything, or worse, linear

SHOTS

One hero per shot, and how each shot hands off

A fade or a slide between every shot

CAMERA (3D)

Lens, height, moves

A slow turntable spin

SOUND

Score, effects, sync

A generic synth pad, or no sound at all

BANNED

What it must not reach for

Everything in the default list below

QA

Whether it looks at frames before rendering

It renders once and reports success

Try it yourself. Give [advanced model] a vague product prompt like "a cool premium 3D animation of my earbuds" and you'll almost always get dark navy space, a glowing ring, bloom, particles and a spinning product. That's the default look, nearly item for item.

The default look, named so you can ban it

  • A centered title on a gradient
  • Everything fading in at once, or fading and sliding up on every element
  • Purple and blue gradients, glow, bloom, lens flares
  • Floating particles as decoration
  • Labels and frame borders in the corners
  • A turntable spin for any 3D product
  • Linear moves
  • A logo slam with a white flash at the end

Paste this under any motion prompt:

plaintext
BANNED: centered title on a gradient; purple or blue gradients; glow, bloom, lens flares;
decorative particles; everything fading in at once; fade-and-slide-up on every element;
text or frame borders in the corners; turntable spins; linear moves; white flash transitions.

Why "avoid a generic AI look" doesn't work: it tells the model what not to be without naming anything, so it swaps one default for its nearest neighbor. Name the exact patterns instead. After every first render, look at what it used anyway and add that to the list. The list grows, and the defaults shrink.

The adjective translator

Adjectives are where the defaults live. Here's what to write instead:

Instead of…

Write this

"premium"

Entrances on ease-out-quint, 600–800 ms. Springs at damping ratio 0.8, no overshoot on text. One accent color. Margins of at least 8% of the frame

"snappy"

UI moves of 150–250 ms. Springs at stiffness 320, damping 30. Stagger of 30 ms between items

"playful"

Springs at damping ratio 0.45–0.55 (15–20% overshoot) on position and scale only. Squash and stretch at 1.15 × 0.87

"cinematic"

24 fps, a 30–35° lens, a camera that never parks (a slow 2% push during holds), motion blur from 4 subframes

"clean"

Two colors plus one accent. One move at a time. A 12-column grid. No shadows except contact shadows

"energetic"

128 BPM, a cut on every beat, scale hits of 1.0 → 1.08 → 1.0 over 6 frames, a layout change every bar

"calm"

90 BPM, holds of at least 1.5 s, ease-in-out-sine, no overshoot, parallax at 1.0 / 0.5 / 0.2

"make it pop"

Scale 1.0 → 1.08 → 1.0 over 6 frames, peaking on the beat, with the shadow lifting at the same time

"it looks like AI"

Ask it to list the defaults it used by name, ban each one, render again

Every adjective is a blank check. A number is a signed one.

Part 4. Setup: two doors in

You can start in the chat app in 30 seconds, or set up a real studio in about 10 minutes. The difference is whether [advanced model] can look at its own frames.

Door 1 · The Claude app, no install

  1. Pick [advanced model] in the model menu.
  2. Paste a prompt from this article.
  3. [advanced model] writes the HTML, and you watch it play in the preview.
  4. Ask for fixes in frame numbers: "the title lands 3 frames late, move it to frame 42".
  5. Download the file, open it in Chrome and screen-record it (Cmd+Shift+5 on a Mac, the Snipping Tool's video mode on Windows).

One tip: ask for a frame counter in a corner and a space bar that pauses, so your notes can name exact frames. Remove both before you record.

A screen recording is fine for a first post. It isn't frame-exact and can drop frames, so for anything you care about, use door 2.

Door 2 · Claude Code, the full studio

With a shell, [advanced model] can render, open the frames, see what's wrong, fix the code and render again, without you copying anything around. Install Claude Code with the one-line installer from Anthropic's docs, then set up the studio.

Effort: when to turn it up

Effort

Use it for

Why

medium (default)

Follow-up fixes, re-renders, small edits

high

New pieces from an L2 or L3 prompt

Room to plan the shots and the code

xhigh

One-liners you want to look great, new pieces with little direction

A flagship launch piece where the first 3 seconds carry everything

Notice the trade-off: effort and direction substitute for each other. Most viral one-shots ran on xhigh or max because a one-liner hands the model every decision. A directed L3 prompt moves that thinking to you, so medium or high often does the job. Shikhar's 3D browser world, one of the biggest pieces of launch week, was captioned "third iteration with [advanced model] medium".

House rules: CLAUDE.md

Claude Code reads CLAUDE.md from your project root on every run. Put the rules there once, and every video you make in this folder follows them without you repeating a word:

plaintext
# Motion studio: house rules

## Render contract
- Every piece is a pure function of time: window.seek(t) paints the frame at t seconds.
- No CSS transitions, no setTimeout/setInterval, no Date.now, no unseeded Math.random.
- Seeded randomness only (mulberry32). Same input, same frame, every run.
- Loops render frames 0..N-1. Frame N-1 must flow into frame 0.
- Render with: node render.mjs <file> --secs S --fps F --w W --h H

## Look
- Banned: centered title on a gradient, purple/blue gradients, glow, bloom, lens flares,
  decorative particles, everything fading in at once, text in the corners, turntable spins.
- One display face, one UI face, one accent color unless the brief says otherwise.
- Something new on screen every 2-4 seconds. One hero move per shot.
- All easing and spring values live in one MOTION object at the top of the file.

## Sound
- Synthesize score and SFX in code unless a track is supplied.
- If a track is supplied, run beats.py first and cut on beats.json.
- Loudness -14 LUFS, true peak under -1 dBTP.
- A sound lands on its picture frame or 1 frame after it, never before.

## Before you show me anything
1. Render one still per shot and a contact sheet. Look at them.
2. Score 1-10: hook in the first 2 s, readability at phone size, motion quality,
   variety, composition, brand accuracy, sound sync.
3. Fix the 3 worst problems. Repeat until every score is 8+.
4. Then do the full render, and report the scores with the file.

Part 5. The engine: render contract + a renderer you can copy

The render contract is the most important block in this article. Paste it under any motion prompt, and every frame [advanced model] makes can be rendered, checked and fixed:

plaintext
RENDER CONTRACT
- Output one self-contained HTML file. Only the libraries I name, pinned to an exact version.
- No network requests except fonts and those pinned libraries.
- Every frame is a pure function of time t in seconds. Expose window.seek(t) that draws exactly that frame.
- No Date.now, performance.now, setTimeout, setInterval or CSS transitions in render mode.
- Randomness only from a seeded generator. If the piece loops, noise must loop too.
- Wait for fonts before the first frame.
- Loops: frames 0..N-1 only. Frame N-1 must flow into frame 0.
- When the URL has ?render=1, turn off the live preview loop.

Each line closes one way a render goes wrong:

Contract line

What breaks without it

Pure function of t

Frame 84 comes out different on every render, so a fix can't be checked

No clocks or timers

A slow machine drops frames and the motion speeds up or stutters

Seeded randomness

Shapes jitter from frame to frame, and every render looks slightly different

Pinned versions

A library update changes a default and your piece changes with it

Fonts first

The first frames render in a fallback font, then jump

Frames 0..N-1

Frame N is frame 0 again. Showing it twice is the hiccup at the loop seam

The page: one HTML file

This is the shape [advanced model] writes when you don't name a framework. It's a complete, working 6-second loop: a title springs in and out, then a grid builds on a stagger and clears. Save it as index.html and open it in Chrome.

htmlbars
<!doctype html>
<meta charset="utf-8">
<style>html,body{margin:0;background:#F4F1EA}canvas{display:block}</style>
<canvas id="c" width="1080" height="1080"></canvas>
<script>
const W = 1080, H = 1080, DUR = 6;                       // a 6-second loop
const INK = '#141413', PAPER = '#F4F1EA', ACCENT = '#D97757';
const ctx = document.getElementById('c').getContext('2d');

// ---------- motion kit: pure functions of time ----------
const clamp = (x, a = 0, b = 1) => Math.min(b, Math.max(a, x));
const easeIn3 = (x) => x * x * x;

// Damped spring from 0 to 1. k = stiffness, d = damping, m = mass.
function spring(t, k = 170, d = 26, m = 1) {
  if (t <= 0) return 0;
  const w0 = Math.sqrt(k / m), z = d / (2 * Math.sqrt(k * m));
  if (z < 1) {                                             // underdamped: overshoots
    const wd = w0 * Math.sqrt(1 - z * z);
    return 1 - Math.exp(-z * w0 * t) * (Math.cos(wd * t) + (z * w0 / wd) * Math.sin(wd * t));
  }
  if (z === 1) return 1 - Math.exp(-w0 * t) * (1 + w0 * t); // critical
  const r1 = -w0 * (z - Math.sqrt(z * z - 1));             // overdamped
  const r2 = -w0 * (z + Math.sqrt(z * z - 1));
  return 1 + (r2 * Math.exp(r1 * t) - r1 * Math.exp(r2 * t)) / (r1 - r2);
}

// Seeded random (mulberry32): the same numbers on every render.
function rng(seed) {
  return () => {
    seed = (seed + 0x6D2B79F5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// ---------- scenes: each one draws itself from its local time ----------
const SCENES = [
  { from: 0, to: 3, draw(t) {                              // title springs in, eases out
      const s = spring(t - 0.1, 220, 22) * (1 - easeIn3(clamp((t - 2.6) / 0.4)));
      ctx.save();
      ctx.translate(W / 2, H / 2);
      ctx.scale(s, s);
      ctx.fillStyle = INK;
      ctx.font = '700 200px system-ui, sans-serif';
      ctx.textAlign = 'center'; ctx.textBaseline = 'middle';
      ctx.fillText('seek(t)', 0, 0);
      ctx.fillStyle = ACCENT;
      ctx.fillRect(-260, 120, 520, 18);
      ctx.restore();
  }},
  { from: 3, to: 6, draw(t) {                              // grid builds on a stagger, then clears
      const r = rng(7);
      for (let i = 0; i < 16; i++) {
        const x = 240 + (i % 4) * 200, y = 240 + Math.floor(i / 4) * 200;
        const grow = spring(t - i * 0.04 - r() * 0.08, 260, 24);
        const gone = easeIn3(clamp((t - 2.0 - i * 0.03) / 0.4));
        const size = 120 * grow * (1 - gone);
        ctx.fillStyle = i % 5 === 0 ? ACCENT : INK;
        ctx.fillRect(x - size / 2, y - size / 2, size, size);
      }
  }},
];

function draw(t) {
  ctx.fillStyle = PAPER; ctx.fillRect(0, 0, W, H);
  for (const s of SCENES) if (t >= s.from && t < s.to) s.draw(t - s.from);
}

window.seek = (t) => draw(((t % DUR) + DUR) % DUR);

// Live preview in a normal browser. Off when rendering (?render=1).
if (!new URLSearchParams(location.search).has('render')) {
  const t0 = performance.now();
  const tick = () => { window.seek((performance.now() - t0) / 1000); requestAnimationFrame(tick); };
  requestAnimationFrame(tick);
}
</script>

Three things to notice. The springs need no simulation: spring(t) returns the value at any t directly, so frame 300 renders without computing frames 0 to 299. The random generator is re-seeded inside every frame, so the stagger is identical on every render. And both scenes start and end on an empty canvas, so frame 359 flows straight into frame 0.

The renderer: render.mjs

It opens the page in headless Chrome, freezes it at every frame, and saves a PNG. With --sub 4 it also saves 4 subframes per frame, spread over half a frame, for real motion blur.

typescript
// render.mjs
// usage: node render.mjs index.html --secs 6 --fps 60 --w 1080 --h 1080 [--sub 4]
import { chromium } from 'playwright';
import { pathToFileURL } from 'node:url';
import { mkdirSync, rmSync } from 'node:fs';

const args = process.argv.slice(2);
const file = args.find((a, i) => !a.startsWith('--') && !(args[i - 1] || '').startsWith('--')) ?? 'index.html';
const opt = (k, d) => { const i = args.indexOf('--' + k); return i >= 0 ? Number(args[i + 1]) : d; };
const SECS = opt('secs', 6), FPS = opt('fps', 60), W = opt('w', 1080), H = opt('h', 1080), SUB = opt('sub', 1);
const N = Math.round(SECS * FPS);                     // frames 0..N-1, never N

rmSync('out/frames', { recursive: true, force: true });
mkdirSync('out/frames', { recursive: true });

const browser = await chromium.launch();
const page = await browser.newPage({ viewport: { width: W, height: H } });
await page.goto(pathToFileURL(file).href + '?render=1', { waitUntil: 'networkidle' });
await page.evaluate(async () => { await document.fonts.ready; });

let n = 0;
for (let i = 0; i < N; i++) {
  for (let j = 0; j < SUB; j++) {
    const t = (i + (j / SUB) * 0.5) / FPS;            // subframes over half a frame = 180° shutter
    await page.evaluate(async (t) => {
      if (window.seek) await window.seek(t);
      for (const a of document.getAnimations()) { a.pause(); a.currentTime = t * 1000; }
      await new Promise((r) => requestAnimationFrame(r));
    }, t);
    await page.screenshot({ path: `out/frames/${String(n++).padStart(5, '0')}.png` });
  }
  if (i % FPS === 0) console.log(`rendered ${i / FPS}s of ${SECS}s`);
}
await browser.close();
console.log(`done: ${n} images in out/frames`);

Every library names its spring knobs differently. One number translates between all of them, the damping ratio:

plaintext
damping ratio = damping / (2 × √(stiffness × mass))

Read it like this: 1.0 never bounces. 0.7–0.85 feels premium. 0.4–0.6 is playful. Under 0.3 is a cartoon. For reference, Remotion's default spring (mass 1, damping 10, stiffness 100) works out to 0.5, and react-spring's default (tension 170, friction 26) to about 1.0.

One rule worth stealing: let position and scale bounce, but never opacity or color. An overshooting fade reads as a flicker.

When one value changes target several times, like a cursor or a container's width, don't restart the spring. Add one spring per change. The motion stays continuous, and any frame still renders on its own:

typescript
// keys = [[time, value], ...] sorted by time. Returns the value at time t.
function track(t, keys, k = 170, d = 26) {
  let v = keys[0][1];
  for (let i = 1; i < keys.length; i++)
    v += (keys[i][1] - keys[i - 1][1]) * spring(t - keys[i][0], k, d);
  return v;
}

// A cursor that moves to x = 620 at 1.0 s, then back to 340 at 2.5 s:
const cursorX = track(t, [[0, 100], [1.0, 620], [2.5, 340]], 320, 30);

120 BPM is the friendliest tempo for video: whole frames at every common frame rate. At anything else, compute each beat from its index, frame = round(i × 60 / BPM × fps), and never add a rounded frame count again and again. At 128 BPM and 30 fps, adding 14 frames per beat puts beat 32 on frame 448 instead of 450. You're 2 frames off the music, and viewers feel it.

The lanes work like this: downbeats (every 4th beat) carry scene changes, beats carry sound effects, and onset peaks measured from the track place the hits exactly (Part 8). Cut on the beat, change the layout on the bar. Changing everything on every beat wears the viewer out.

Part 8. Sound: [advanced model] can't hear, so it measures

[advanced model] can't listen to audio. Everything it does with sound is numbers: timestamps, frequencies, loudness. That turns out to be an advantage. It never "feels" sync. It measures it.

Two rules come before any code:

  1. The picture must work in silence. X autoplays video muted, so most people see your piece before they hear it.
  2. A sound lands on its picture frame or one frame after, never before. In real life light arrives before sound, so a slightly late sound feels natural. An early one feels wrong immediately.

Path A · You bring a track: measure it first

Save this as beats.py. It turns your song into a list of times the animation can cut on:

python
# beats.py   usage: python beats.py audio/track.wav > beats.json
import sys, json
import numpy as np, librosa

y, sr = librosa.load(sys.argv[1], sr=None, mono=True)
tempo, beat_frames = librosa.beat.beat_track(y=y, sr=sr)
beats = librosa.frames_to_time(beat_frames, sr=sr)
onsets = librosa.onset.onset_detect(y=y, sr=sr, units="time")

json.dump({
    "bpm": round(float(np.atleast_1d(tempo)[0]), 2),
    "beats": [round(float(b), 3) for b in beats],           # cuts and state changes
    "downbeats": [round(float(b), 3) for b in beats[::4]],  # big moments (assumes beat 0 is a downbeat)
    "onsets": [round(float(o), 3) for o in onsets],          # exact hits for sound effects
}, sys.stdout, indent=1)

Then tell [advanced model]: "Read beats.json. Put scene changes on downbeats, state changes on beats, and every visual hit on the nearest onset." Check that the first downbeat really is the start of a bar. If it isn't, tell it which beat is, and it'll shift the grid.

Path B · No track: synthesize it in code

No samples, no downloads, no licenses. Every effect is a few lines of math, and the same cue list produces the same file every time:

python
# sfx.py   usage: python sfx.py cues.json out/sfx.wav
# cues.json: [{"t": 0.5, "type": "click"}, {"t": 1.0, "type": "thump"}, ...]
import sys, json
import numpy as np, soundfile as sf

SR = 48000
cues = json.load(open(sys.argv[1]))
out = np.zeros(int((max(c["t"] for c in cues) + 1.5) * SR))
rng = np.random.default_rng(42)                     # seeded: same file every run

def tone(dur, f0, f1, decay, amp):                  # a pitch sweep with an exponential decay
    t = np.arange(int(dur * SR)) / SR
    phase = 2 * np.pi * np.cumsum(np.linspace(f0, f1, t.size)) / SR
    return amp * np.sin(phase) * np.exp(-t * decay)

def noise(dur, amp):                                # white noise that swells in and out
    t = np.arange(int(dur * SR)) / SR
    return amp * rng.uniform(-1, 1, t.size) * np.sin(np.pi * t / dur)

VOICES = {
    "click":  lambda: tone(0.04, 2200, 1800, 120, 0.35),
    "pop":    lambda: tone(0.12, 500, 1400, 35, 0.40),
    "thump":  lambda: tone(0.45, 110, 45, 9, 0.90),
    "whoosh": lambda: noise(0.35, 0.18),
}

for c in cues:
    s = VOICES[c["type"]]()
    i = int(round(c["t"] * SR))
    out[i:i + s.size] += s[: max(0, out.size - i)]

out /= max(1.0, np.abs(out).max() / 0.89)          # keep peaks under about -1 dBFS
sf.write(sys.argv[2], np.stack([out, out], axis=1), SR)

Ask [advanced model] to write cues.json from the same timeline as the picture, so every sound already knows its frame. Want a score too? Ask for "an original 120 BPM track synthesized in code: kick on every beat, a bass line, a pad, no samples". It's the same idea with longer notes.

Part 9. Seamless loops and export for X

The last mile is the part tutorials skip and viewers notice first.

Loops that never show the seam

A loop is seamless when frame N-1 flows into frame 0 as smoothly as any other two frames. Five rules get you there:

  1. Render frames 0 to N-1, never N. Frame N is frame 0 again, and showing it twice is the hiccup.
  2. Drive everything periodic from one phase, phase = t / DUR, going from 0 to 1 over the loop.
  3. Use whole-number cycles. A square that turns exactly 90° per loop lands on itself. A wave that completes exactly 3 cycles ends where it started.
  4. Make organic noise loop by walking a circle through 2D noise, so it ends where it began.
  5. Make frame 0 a finished composition. It's what people see while the video loads.
typescript
const phase = (t % DUR) / DUR;                      // 0 -> 1 over the loop
const angle = phase * Math.PI / 2;                  // exactly 90° per loop
const bob = Math.sin(phase * 2 * Math.PI * 3);      // exactly 3 cycles per loop

// Looping noise: walk a circle through any seeded 2D noise function
const a = phase * 2 * Math.PI;
const wobble = noise2D(Math.cos(a) * 0.8, Math.sin(a) * 0.8);

"One hero move per shot. Secondary moves travel 60% as far and start 150 ms later. Ambient motion under 5% of the hero's travel."

Shapes shimmer or jitter between frames

Unseeded Math.random called per frame

"Use a seeded generator re-seeded inside every frame. No Math.random anywhere."

Two renders of the same frame differ

A clock, a timer or a CSS transition

"Apply the render contract: pure function of t, no Date.now, timers or CSS transitions in render mode."

A hiccup at the loop seam

Frame N was rendered, or a cycle isn't whole

"Render frames 0..N-1 only. Make every periodic motion complete a whole number of cycles. Compare frame N-1 with frame 0."

Text is blurry when it scales

Text drawn small and scaled up, or will-change on scaled layers

"Draw text at its largest size and scale down, never up. Remove will-change from anything the camera scales."

Wrong font in the first frames

Capture started before the fonts loaded

"Wait for document.fonts.ready before the first frame."

Text overlaps during swaps

Old and new content swap on the same frame as the morph

"New content enters 4 frames after the morph starts. Old content leaves 4 frames before it."

A dead stretch in the middle

Nothing new for 2+ seconds

"Something new must happen on every beat. Show me the beats where nothing changes, and fill them."

The product UI looks invented

[advanced model] redrew it from memory

"Screenshot the real UI with Playwright, save it to ./assets, and animate crops of the real screenshots."

3D looks like plastic or neon

Default bloom and glow, unnamed materials

"No bloom, no glow. Materials: [name] roughness [x], clearcoat [y]. Key, fill and rim lights with exact colors and strengths."

Sound feels early or late

Hits placed by guess

"Run beats.py. Place every visual hit on its onset. Each sound peaks on its frame or 1 frame after, never before."

Great on a laptop, silent on a phone

The mix lives under 60–150 Hz

"Measure the energy in the 150 Hz–6 kHz band. Move the bass up an octave or add harmonics until the phone band carries the mix."

The GIF drifts off the beat

24/30/60 fps delays get rounded in GIFs

"Export the GIF at 25 fps."

"Preview renders at 540p with --sub 1. Final render only at full size."

Defaults you haven't banned yet

FAQ

Can [advanced model] make a video file by itself? No. It writes code that draws the frames. A browser renders them, and ffmpeg encodes the MP4. In Claude Code, [advanced model] runs that whole pipeline itself.

Do I need After Effects? No. A browser and the Claude app are enough to start. Claude Code, ffmpeg and Playwright give you frame-exact renders.

Is "one prompt" real? Sometimes, at L1. Most of the pieces that went viral were L3 or L4 briefs, or had follow-ups. Two to four review rounds is normal.

Why does my one-prompt video look mid? Every line you leave out, [advanced model] fills with a default. Add a look, a reference, a ban list and a QA line (Part 3).

Which effort setting should I use? Medium for fixes, high for new directed pieces, xhigh or max for vague prompts and flagship launches (Part 4).

How long does it take? From about 15 minutes for a one-liner to 12 hours for an overnight director's brief (Part 2).

Can it use my brand? Yes. Give it the URL and tell it to screenshot the real UI. Never let it redraw the UI from memory.

Can it copy the style of a video I like? It can take the grammar: pacing, palette, type, transitions. Ask it to extract frames, write a style guide and wait for your OK. Leave the content, characters and logos behind.

Can it do sound? Yes. It either synthesizes everything in code or measures the track you give it. It can't hear, so it measures (Part 8).

Can it do 3D and characters? Yes. Three.js for 3D, a character bible plus the principles table for characters, and route C for physics that's hard to hand-code.

What does it cost? In the chat app, it runs on your plan. Through the API it depends on length and effort. As one data point, Vox reported about $90 at API prices for a 5.5-hour overnight run.

Glossary

Term

Meaning

seek(t)

The function that draws the exact frame for time t. The heart of every render

Render contract

The rules that keep every frame reproducible (Part 5)

Frame N-1

The last frame of a loop. It must flow into frame 0

Contact sheet

Many frames tiled on one image, read like a storyboard

Strip

Consecutive frames in a row, used to catch pops and overlaps

Damping ratio

One number for spring bounce. 1.0 = no bounce, 0.5 = playful

Stagger

The delay between elements that move one after another

Beat grid

Frame numbers for every beat: fps × 60 / BPM frames per beat

Downbeat

The first beat of a bar, every 4th beat in 4/4. Big moments go here

Onset

The measured start of a sound in a track. Hits go here

LUFS

Perceived loudness. -14 LUFS is a common target for web video

dBTP

True peak level. Keep it at -1 or lower

CRF

x264 quality setting. Lower is better: 16–18 looks visually lossless

yuv420p

The pixel format every phone and browser can play

faststart

Puts the MP4 index at the front, so playback starts at once

Several renders inside one frame, blended into real motion blur
