Design Engineering: Build a Motion Studio Around [advanced model]

S 🫧 (@dyfwsammy) · Source sur X

Motion design lives in an awkward gap. Designers think in feel: weight, rhythm, overshoot. Engineers think in state, performance, and edge cases. A design engineer works in the middle, and with a strong model like [advanced model], one person can now run something that behaves like a small motion studio.

The model doesn't replace your taste. It becomes the production layer: it writes the tokens, builds the prototypes, and audits the work, while you decide what feels right. Here is how to set that up, with code.

1. Start with a motion language

Most products feel inconsistent because every animation was invented in isolation. Before generating anything, define the vocabulary once.

Write a short MOTION.md in your repo covering durations, named easings, what never animates, and the reduced-motion behavior. Then encode it as tokens.

CSS tokens

:root {
  --dur-fast: 120ms;
  --dur-base: 240ms;
  --dur-slow: 400ms;

  --ease-enter: cubic-bezier(0.16, 1, 0.3, 1);
  --ease-exit: cubic-bezier(0.7, 0, 0.84, 0);
  --ease-emphasis: cubic-bezier(0.34, 1.56, 0.64, 1);
}

@media (prefers-reduced-motion: reduce) {
  :root {
    --dur-fast: 0.01ms;
    --dur-base: 0.01ms;
    --dur-slow: 0.01ms;
  }
}

The same tokens for JavaScript animation libraries

// tokens.ts
export const tokens = {
  duration: { fast: 0.12, base: 0.24, slow: 0.4 },
  ease: {
    enter: [0.16, 1, 0.3, 1],
    exit: [0.7, 0, 0.84, 0],
    emphasis: [0.34, 1.56, 0.64, 1],
  },
  spring: {
    sheet: { type: "spring", stiffness: 380, damping: 32 },
    snappy: { type: "spring", stiffness: 520, damping: 36 },
  },
} as const;

Give MOTION.md to [advanced model] at the start of every session (a project instruction works well). Every component it writes now inherits your studio's voice.

2. Prototype by describing physical behavior

The fastest loop in the studio is a conversation. Describe the feel, not the implementation:

"A bottom sheet that feels heavy. It resists upward drag, settles with a slight overshoot, and dismisses on a fast downward flick even if the drag distance is short."

That maps cleanly to springs, elasticity, and velocity thresholds. A typical result, using the motion library for React:

import { AnimatePresence, motion, useReducedMotion, PanInfo } from "motion/react";
import { tokens } from "./tokens";

type SheetProps = {
  open: boolean;
  onClose: () => void;
  children: React.ReactNode;
};

export function Sheet({ open, onClose, children }: SheetProps) {
  const reduce = useReducedMotion();

  function handleDragEnd(_: unknown, info: PanInfo) {
    const fastFlick = info.velocity.y > 800;
    const farEnough = info.offset.y > 120;
    if (fastFlick || farEnough) onClose();
  }

  return (
    <AnimatePresence>
      {open && (
        <motion.div
          role="dialog"
          aria-modal="true"
          initial={{ y: "100%" }}
          animate={{ y: 0 }}
          exit={{ y: "100%" }}
          transition={reduce ? { duration: 0 } : tokens.spring.sheet}
          drag="y"
          dragConstraints={{ top: 0, bottom: 0 }}
          dragElastic={{ top: 0.08, bottom: 0.6 }}
          onDragEnd={handleDragEnd}
          style={{ position: "fixed", inset: "auto 0 0 0", touchAction: "none" }}
        >
          {children}
        </motion.div>
      )}
    </AnimatePresence>
  );
}

Notice what you'd ask the model to do next: expose stiffness, damping, and the flick threshold in a debug panel so you can tune by feel on a real phone instead of guessing in text.

3. Enforce the spec with a cheap linter

Not everything needs a model. A plain script catches the obvious drift for free and runs in CI:

// scripts/motion-lint.ts
import { readFileSync } from "node:fs";
import { globSync } from "glob";

const files = globSync("src/**/*.{css,tsx,ts}", { ignore: "src/tokens.*" });
const rules = [
  { re: /cubic-bezier\(/, msg: "Use an --ease-* token, not a raw curve" },
  { re: /\b\d+ms\b/, msg: "Use a --dur-* token, not a raw duration" },
  { re: /transition:\s*all\b/, msg: "Never transition: all" },
];

let failed = false;
for (const file of files) {
  readFileSync(file, "utf8").split("\n").forEach((line, i) => {
    for (const { re, msg } of rules) {
      if (re.test(line) && !line.includes("var(--")) {
        console.log(`${file}:${i + 1}  ${msg}`);
        failed = true;
      }
    }
  });
}
process.exit(failed ? 1 : 0);

4. Add a model-powered review pass

The linter catches syntax. The model catches judgment calls: interruptibility, layout-triggering properties, missing reduced-motion handling. Wire [advanced model] into a review script:

// scripts/motion-review.ts
import Anthropic from "@anthropic-ai/sdk";
import { readFileSync } from "node:fs";

const client = new Anthropic(); // reads ANTHROPIC_API_KEY

const spec = readFileSync("MOTION.md", "utf8");
const file = process.argv[2];
const code = readFileSync(file, "utf8");

const res = await client.messages.create({
  model: "[advanced model]",
  max_tokens: 1500,
  system:
    `You are a skeptical senior motion engineer. Review the code strictly ` +
    `against this spec:\n\n${spec}\n\n` +
    `Check: animating layout properties, interruptibility, reduced-motion ` +
    `handling, focus management, and token usage. ` +
    `Reply with a JSON array of {line, severity, issue, fix} and nothing else.`,
  messages: [{ role: "user", content: code }],
});

const text = res.content
  .filter((b) => b.type === "text")
  .map((b) => b.text)
  .join("");

try {
  console.table(JSON.parse(text));
} catch {
  console.log(text); // fall back to raw output
}

Run it on every new component: npx tsx scripts/motion-review.ts src/Sheet.tsx. Treat the output as a first pass from a tireless reviewer, not a verdict.

5. Keep decision records

Every good motion choice becomes a future argument: why 280ms and not 240ms, why the modal doesn't bounce. Have the model draft a short record after each component:

## Sheet: settle behavior
- Decision: spring (stiffness 380, damping 32), no tween
- Why: tween felt weightless; spring gives natural overshoot and is interruptible
- Rejected: --ease-emphasis curve (overshoot too long, felt toy-like)
- Reduced motion: instant transition, no drag elasticity
  • Taste. Whether it actually feels right in the hand.
  • Restraint. Deciding what shouldn't animate at all.
  • Real-device testing. Frame drops and gesture feel don't show up in code review.
  • Brand fit. Playful versus annoying is contextual.

A one-week starter plan

  1. Write a one-page MOTION.md and the token files above.
  2. Add the linter to CI.
  3. Build one component end to end (a toast, a sheet, or a tab transition) with tunable parameters.
  4. Run the review script, fix what it finds, then test on a physical device.
  5. Write the decision record, then repeat.

After a handful of components you'll have a battle-tested spec, a token system, an automated quality bar, and a rhythm for working with the model.

The takeaway

Design engineering with a model like [advanced model] isn't about automating taste away. It's about collapsing the distance between "I can feel what this should be" and "it's running in the app." Bring a clear point of view, encode it as a spec, and let the model handle the volume.
